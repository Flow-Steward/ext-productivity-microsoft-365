# v0.2 Calendar: design notes

Task: `bmad-project/docs/plans/2026-11-22-microsoft-365-extension-v0.2-task.md`, §2 and
D2. This file lists the shared edits the lead must make, the deviations from D2, and
the live-verify items. Nothing here is committed.

## What exists

- `calendar_ops/` (not `calendar`, which would shadow the standard library module):
  - `operations.py`: `OPERATIONS`, `QUERY_IDS`, `handle_query`, as in `mail/operations.py`.
  - `reads.py`: `test_calendar_connection`, `list_calendars`, `list_events`, `get_event`.
  - `writes.py`: `create_event`, `update_event`, `cancel_event`, `respond_to_event`
    (all `effectful=True`, all `retry="none"`).
  - `schedule.py`: `find_free_time`.
  - `access_check.py`: `check_calendar_access` (setup action, reads only).
  - `common.py`, `zones.py`: limits, time input, event output, IANA and Windows zones.
- `contracts/parts/calendar/`: `operations.yaml`, `step_ui.yaml`, `actions.yaml`,
  `external_effects.yaml`, `resource_queries.yaml` (`calendars_user`, `calendars_app`).
- `tests/test_calendar_*.py` (fake Graph only). `test_calendar_fakes.py` holds the
  in-memory calendar and no tests.

The step key uses the v0.1 mail property `FlowStewardIdempotencyKey` in property set
`b9fd5293-1be4-448e-b08f-b4467c228ad8` (`mail.send.KEY_PROPERTY_ID`, imported, not
copied).

## Deviations from D2

1. **Cancel confirmation and Deleted Items.** After an ambiguous cancel, the event
   counts as cancelled when the re-read returns 404 or `isCancelled: true`. Graph's
   `event` has no parent folder, so "the event is in Deleted Items" cannot be detected
   with a documented call. An event that still reads as active is reported as
   `timeout_unknown`: the safe direction. The live check decides whether a third rule is
   needed.
2. **An appointment without attendees is deleted** (`DELETE /events/{id}`, which moves
   it to Deleted Items) instead of cancelled. `cancel` is a meeting action. The result
   says `confirmation: deleted`, `attendees_notified: none`.
3. **Re-run guard before `create_event`.** Before the POST, the event collection is
   searched by the step key, like the v0.1 send flow's Sent Items check. A hit returns
   `confirmation: already_exists` without a second event. This costs one GET per
   create.
4. **Client-side date check.** A key match is success only when its start equals the
   requested start. A key match with another start is `timeout_unknown`, as are several
   matches; every id is in the error message.
5. **`respond_to_event` pre-checks.** The event is read first. If the attendee's
   response already equals the request, nothing is sent (`changed: false`,
   `response_sent: not_sent`). The organizer's own event is `invalid_payload`.
6. **`update_event` and HTML bodies.** Outlook rewrites stored HTML, so `body_html`
   never compares equal after an ambiguous PATCH, and that case is always
   `timeout_unknown`. `body_text` is compared with whitespace collapsed. `start` and
   `end` must be given together. `attendees` / `optional_attendees` replace the list.
7. **Time zones are strict.** A zone must be an IANA name known to `zoneinfo` or a
   Windows name in the CLDR table (`calendar_ops/zones.py`); anything else is
   `invalid_payload`. A date-time without an offset needs `time_zone`. Graph receives
   the caller's zone name. Results add `start_local` / `end_local`, which are `null`
   when the original zone is not resolvable (for example `Customized Time Zone`).
8. **`find_free_time` details** (D2 lists only the inputs):
   - `include_weekends` (default false, Monday to Friday) and `max_slots` (default 20,
     at most 100) are additions;
   - working hours are `HH:MM` on a quarter hour, the slot interval is a multiple of
     15 minutes, and the duration is a multiple of 5 minutes;
   - `availabilityViewInterval` is fixed at 15 minutes, and the Graph window is aligned
     to quarter hours (UTC);
   - `tentative`, `busy`, `oof` and an `unknown` item status block a slot;
     `workingElsewhere` does not;
   - a view shorter than the window is `no_data`, so the address is unresolved;
   - the organizer is not added automatically, so the workflow must list them.
9. **`getSchedule` is a POST that only reads.** It uses `retry="idempotent"`. An
   unanswered call is `provider_unavailable` / `network_failure`, never
   `timeout_unknown`, and `find_free_time` is not an external effect.
10. **`list_events` also takes `time_zone`** for a window given in local time.
11. **`check_calendar_access`** reads the default calendar of the connection's mailbox
    (expected: allowed) and of the control mailbox (expected: refused). Verdicts:
    `restricted`, `broad_access`, `inconclusive`. It has no write probe, because the
    Exchange role grants read and write together.
12. **Every operation is also an action** in `actions.yaml`, as in mail.
13. **Result vocabularies:**
    - `create_event.confirmation`: `created`, `extended_property`, `already_exists`;
    - `cancel_event.attendees_notified`: `requested`, `unknown`, `none`;
    - `respond_to_event.response_sent`: `requested`, `unknown` (after an ambiguous
      call), `not_requested`, `not_sent`.
14. **Effect kinds.** The effect kinds are `calendar_event_create`, `_update`,
    `_cancel` and `_response`, on channel `microsoft_outlook_calendar`. Core treats
    them as free-form; Core's grounding reads none of them as `delete` or `send`.
15. **`user_not_found` is not used by the calendar.** An unknown address in
    `find_free_time` is reported per address, not as an error.
16. **No `online_meeting` on `update_event`** in v0.2.
17. **`list_events` cursors reuse `mail/cursors.py`** (prefix `m365m1.`). They are
    bound to the mailbox, calendar, window and limit.

## Live-verify items (D7 step 1)

Calendar writes and lookup:
- What a POST that repeats the same `transactionId` does: returns the first event,
  fails, or creates a second event. The extension never repeats the POST, so test this
  by hand.
- Whether the property filter combines with a `start/dateTime` filter. The extension
  never combines them.
- The property filter with `$expand` works on `/events` and on
  `/calendars/{id}/events`, in both modes, and how long it takes on a large calendar
  (it runs before every create).
- Graph accepts IANA names (`Europe/Berlin`) in `dateTimeTimeZone.timeZone` on create
  and update.
- `onlineMeeting.joinUrl` is in the 201 response of a create with `isOnlineMeeting`.
- What `GET /events/{id}` returns after the organizer cancels: 404, `isCancelled`, or
  the item in Deleted Items (deviation 1).
- `cancel` on an appointment without attendees: fails, or works like `DELETE`
  (deviation 2).
- After `decline`, whether the event leaves the calendar and what a re-read by id
  returns.
- Immutable ids (`Prefer: IdType="ImmutableId"`) for events, and that they survive
  cancel and decline.

Reads:
- The `calendarView` nextLink keeps the `/me/` or `/users/{mailbox}/` path (otherwise
  `invalid_cursor`). This is the same item as for mail.
- `/calendar/calendarView` and `/calendars/{id}/calendarView` honour
  `Prefer: outlook.timezone="UTC"`.
- The values of `originalStartTimeZone`: Windows names, `tzone://Microsoft/Utc`, or
  `Customized Time Zone`.

`getSchedule`:
- With a window aligned to quarter hours, `availabilityView` has exactly window/15
  characters.
- The shape of an unknown or external address: `error` with `responseCode`, or a `?`
  view.
- `scheduleItems` times come back in UTC under `Prefer: outlook.timezone="UTC"`. The
  code also parses an explicit zone.
- App-only: whether the RBAC management scope also limits whose schedules can be read
  (D2).
- Delegated: free/busy of people outside the tenant.

App-only RBAC:
- `Application Calendars.ReadWrite` on a scope lets `cmr@` read events, create a
  meeting and call `getSchedule`; each is checked separately.
- A mailbox outside the scope is refused (`mailbox_access_denied`), and
  `check_calendar_access` says `restricted`.
- `accept`, `decline` and `cancel` work app-only.

Runtime:
- `zoneinfo` finds tz data in the Core runtime. `requirements-runtime.txt` has
  `tzdata`; the extension declares no Python requirements.

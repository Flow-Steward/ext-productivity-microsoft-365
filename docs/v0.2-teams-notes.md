## 4. Deviations

1. **Every post is HTML.** A `body_text` is HTML-escaped with `<br>` line breaks, so the
   marker and mentions work the same way for both body kinds.
2. **Mentions** are a line of `<at>` tags at the start of the message, in the order given
   (no placeholders inside the body). An address is resolved with `GET /users/{address}`,
   which needs `User.ReadBasic.All` (open question 1). Unknown address → `user_not_found`
   before anything is posted.
3. **File links** are HTML links in the body, not Graph `reference` attachments: those
   need the item's direct SharePoint URL plus an `<attachment id>` tag, and v0.1's
   `create_share_link` returns a sharing link. Links must be `https`.
4. **The marker** carries a 24-hex SHA-256 token of the step key, never the key itself.
   It is stripped from caller HTML before posting (no spoofing) and from all
   `list_messages` output, whichever strategy wrote it. Swap the strategy with
   `teams.markers.DEFAULT_MARKER`.
5. **No pre-post lookup** (mail checks Sent Items before sending). The ambiguous
   lookup runs only after an ambiguous POST: 3 reads of the newest 20 messages, 2 s
   apart. A failed lookup read counts as "not found".
6. **`post_chat_message` with `user`** creates the 1:1 chat with `POST /chats`
   (`retry="idempotent"`: Graph returns the existing 1:1 chat). The user is bound by
   address (`users('ana@…')`). A 400/404 there is `user_not_found`; an ambiguous chat
   create is `provider_unavailable`, retryable, with no message posted. The message is
   validated and sized **before** the chat is created.
7. **`actions.yaml` part added** (not in the four listed): every v0.1 operation also has
   an action row, and `merge_contracts.py` merges `actions` parts into
   `ui/actions/actions.yaml`.
8. **Pickers.** Core passes no dependent field to a resource query, so `channels_user`
   lists the channels of every joined team (first 50 teams) with value
   `team_id/channel_id` (the route format) and label `Team / Channel`. Teams the user
   cannot read are skipped. `chats_user` searches topic and member names, with a cursor.
9. **`list_messages`** skips system events and deleted messages, returns text only (HTML
   converted), and filtered pages resume mid-page through the cursor (Graph page link +
   offset). Channel messages are not re-sorted (Graph's own order, see live-verify).
10. **Webhook opener.** The default is the SDK's `open_pinned_url`: a dedicated opener
    with redirects already disabled (`_NoRedirectHandler`), DNS pinning and private
    addresses refused. It is not `GraphTransport`. Tests inject `FakeOpener`.
11. **Webhook outcomes beyond the task:** 429 → `webhook_rejected` but retryable with
    `Retry-After` (nothing was posted); a request that never left (pinned-peer refusal,
    connection refused, DNS failure) → `network_failure`, no effect, retryable; any other
    unexpected exception → `timeout_unknown`. Exceptions are raised without their cause
    (`HTTPError` holds the URL). URL errors: not `https`, credentials, a port other than
    443, malformed → `invalid_connection`; host outside the suffixes →
    `egress_host_not_allowed`. Cards above 28 KB → `message_too_large`.
12. **Size check** counts the UTF-8 bytes of the whole `chatMessage` JSON (body, marker,
    mentions, subject) against 28 × 1024. A Graph 413 also maps to `message_too_large`.
13. **Input mapping rule codes** `body_required`, `chat_target_required`,
    `channel_required` are Core mapping errors (like mail's `body_source_ambiguous`).
14. **Category** `chat` for all Teams operations (new category key).

## 5. Live verify (D7 step 2 and D4)

**Graph, `m365_teams_user`**
- Does the HTML comment marker survive in the stored `body.content`? If not, switch
  `DEFAULT_MARKER` to `ZeroWidthMarker()` and check that the zero-width sequence survives.
- A forced ambiguous post: the lookup finds the marker (needs `ChannelMessage.Read.All`
  with admin consent; without it the lookup fails and the step is `timeout_unknown`).
- Channel message order from `GET /teams/{t}/channels/{c}/messages` (`$orderby` is not
  supported there): newest first?
- `$top=50` with `$expand=members` on `/me/chats`; `$orderby=createdDateTime desc` on
  `/chats/{id}/messages`.
- nextLink paths stay under `/v1.0/me/chats`, `/v1.0/teams/{t}/channels/{c}/messages`
  and `/v1.0/chats/{id}/messages`; otherwise cursors fail with `invalid_cursor`.
- Mentions: `GET /users/{address}` scope, and that the `<at>` + `mentions` shape notifies.
- `POST /chats` oneOnOne with a UPN bind: the existing chat comes back (no duplicate);
  what an alias address (mail ≠ UPN) and an unknown address return (400 or 404).
- What Graph returns above the size limit (413 or 400), and whether 28 × 1024 UTF-8
  bytes of JSON is the right measure.
- `subject` on a channel root post; replies at `/messages/{id}/replies`.
- 404 vs 403 vs 400 for an unknown team, channel, chat and thread root.
- Deleted messages: `deletedDateTime` set and/or empty body.

**Workflows webhook, `m365_teams_webhook`**
- Record the real trigger host; confirm the two suffixes (`*.environment.api.powerplatform.com`
  for new flows, `*.logic.azure.com` for older ones).
- The flow's answer: 202 on accept; status for a disabled or deleted flow, and for
  *Who can trigger* not set to *Anyone*.
- The card **appears** in the bound channel (Adaptive Card 1.4, severity color, FactSet,
  Open button); a 2xx alone is not proof.
- No redirect is followed (3xx → `webhook_rejected`).
